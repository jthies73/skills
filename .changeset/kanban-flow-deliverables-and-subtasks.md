Add an optional **kanban flow**, mirrorable on GitHub and GitLab, and settle the two levels of work it needs. No new skill: a board is a right-hand column in one mapping file, so the skills read a different table rather than learning new behaviour.

`setup-matt-pocock-skills` now asks one question about labels, **do you run a kanban board**, with yes as the default. Yes writes the board mapping: five lists (Backlog / TODO / In Progress / Review / On Hold) plus the host's built-in Closed list as Done, `wontfix` labelled so closed-and-shipped stays distinguishable from closed-and-discarded, and the in-flight roles included rather than opt-in, since `In Progress` and `Review` are columns. No writes the flat mapping, one label per role, which is what shipped before. Setup also stops writing a mapping it hasn't checked: it lists what the tracker has, reports each label as present or missing, and offers to create the missing ones. On GitLab it asks for the group path first, because a group-level board can only build its lists from group labels.

The flow needs two levels of work, and they are now named. A **Deliverable** is one unit of delivery: one issue, one branch, one merge request, several commits, one card. A **Subtask** is a vertical slice inside it, sized for one fresh context window, worked in order on the Deliverable's branch, and never carrying a column label, which is what keeps it off the board. `to-tickets` produces one Deliverable with ordered Subtasks and moves it into the ready role as its final step, so a ready column is earned by having both a filled spec and published Subtasks. Blocking edges narrow to **between Deliverables only**: inside one, sequence is the edge. Where a spec turns out to be more than one shippable merge request, `to-tickets` says so and creates sibling Deliverables with edges between them, and the original issue becomes a container that leaves the board. A wide refactor's expand / migrate / contract steps are that case by construction.

`implement` claims the Deliverable, works its Subtasks in order, and closes each one as it finishes, so the child list reads as a progress bar. It refuses unrefined work whoever named it, recommending `/triage` by name, and it stops at a Subtask that needs a person rather than guessing, pointing at `/wizard`. `land-the-work` references and closes the **Deliverable only**. `triage` excludes Subtasks from discovery: the untriaged bucket is issues with neither a state nor a readiness label, which on a board is a raw report and nothing else.

Why the Deliverable and not the Subtask is the unit is recorded as an ADR, along with the assumption it rests on: a run of Subtasks lands within about two days. Subtask-as-unit buys faster always-shippable iteration but makes a parent's column derived state and empties the Review column, since every slice merged as it lands has already been reviewed by the time the parent gets there.

`to-spec` stops labelling the spec `ready-for-agent` on publish, which was the most-reported rough edge on it: an AFK agent polling that label would try to build a whole unsplit spec in one run. It now writes the spec into the Deliverable and leaves the state role alone, so readiness means both specified and split. Where the build is small enough to skip `to-tickets`, it applies the ready role itself and says so.
