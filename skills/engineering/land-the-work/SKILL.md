---
name: land-the-work
description: "Land finished work on a branch of its own, commit it as a Conventional Commit, and offer to push and open the merge/pull request. Use when work is finished and sitting uncommitted, when the user asks to branch, commit, or open a PR/MR, or when a skill that built something closes out."
---

Finished work is not delivered while it sits in a dirty tree. Land it.

1. **State the shape, then check for an override.** The default is [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): a subject of `type: summary` in the imperative, `type` from `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `build`, `ci`, `style`; and a branch name of `type/slug` (`type/ticket-slug` when a ticket exists). That default holds even where the repo's own history doesn't already look like it, since a history of unconventional commits is exactly the debt this fixes going forward. Check `CONTRIBUTING.md`, `AGENTS.md`, and `CLAUDE.md` for a documented override (a different subject shape, a custom type list, a required footer) and a commitlint config (`.commitlintrc*`, `commitlint.config.*`) the same way, and follow either where one exists. Skim `git log --oneline -30` for how the repo references tickets in a footer, and `git status -sb` for where you are. Settle here whether merging should close the referenced issue (the tracker config decides; step 7 spends it), so the footer you write in step 5 doesn't need amending. Done when you can state which subject shape is in force, how tickets get referenced, and whether merging closes them, all quoted from what you just read.

2. **Pick the base branch, and say which one you picked.** The default branch (usually `main`) is the default answer. Branch from a feature branch instead when this work builds on commits that live only there, so the base already carries what the work depends on. `git fetch`, then compare the base with its remote: a base that is behind gives the reviewer a diff full of other people's changes. Where both candidates are defensible, ask before branching.

3. **Branch, unless you are already on the right branch.** Name it in the shape from step 1 (`fix/842-flaky-e2e-timeout`, `feat/notification-preferences`). The commit lands on a ticket branch, created here or already checked out; the default branch stays untouched.

4. **Stage the work, and only the work.** Read `git status --short` in full, then add the paths this work touched. Where something unexpected is dirty (a stray edit, a generated file, another task's leftovers), ask rather than sweeping it in. Two unrelated pieces of work in one tree are two commits, staged separately. Done when `git diff --cached --stat` is exactly the work.

5. **Write the commit in the shape from step 1.** Subject as `type: summary`, then a body carrying what a reviewer would otherwise have to reconstruct: the decisions behind the change, the constraint that forced an odd-looking choice, and anything the work uncovered and deliberately left alone. Footer referencing the ticket the way step 1 found tickets referenced. Where a hook rejects the commit, fix what it flagged and commit again, keeping the hook in the loop.

6. **Offer to push and open the request, then follow through only if told to.** Report the landing first: branch, SHA, subject. Ask whether to push and open the merge/pull request now, since both put the work in front of other people. On yes: push the branch, then create the request (`gh pr create` on a GitHub remote, `glab mr create` on GitLab, chosen from `git remote -v`), titled from the commit subject. If the tracker config names a default reviewer, pass it (`--reviewer <name>`); if it names none, don't. Fill the repo's own PR/MR template if it has one (`.github/PULL_REQUEST_TEMPLATE.md`, `.gitlab/merge_request_templates/`); otherwise write a description carrying two things: the feature description (what changed and why, in the reader's terms, not a diff summary) and the ticket it's for, referenced the way step 1 found tickets referenced. On no, or where neither CLI is configured, stop at the commit and report as before. Where the triage-labels config names an **in-review role**, also move each referenced issue into it once the request is open, clearing whichever state it was in before.

7. **Reference the issue so merging closes it.** Where the tracker config says merging should *not* close the referenced issue, skip to the last sentence of this step: write `Refs #123`, one per issue this work touches, finished or partial, and report which issues moved rather than which will close.

   Otherwise: GitHub and GitLab close a linked issue on merge only where the description carries a closing keyword; a bare `#123` links and leaves it open, which is how issues outlive the work that finished them. Leaves nothing of the issue undone: `Closes #123`, one per issue finished. Does part of it: `Refs #123` plus what is still outstanding, since a half-answered issue closed by a keyword is worse than one left open. Cannot tell: ask. Two silent failures to check for: the keyword fires only on merge into the default branch, and it reaches the host's own issues only, so a Jira, Linear, or Asana ticket closes through that tracker's integration or not at all. Report which issues will close before the merge happens.
